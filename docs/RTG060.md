# OpenSWOS on a 68060 with an RTG screen

The WarpOS build (docs/WARPOS.md) without the PowerPC: the chunky target without SDL — 8bpp
chunky renderer, hosted libc, `SWOS.ini`, JSON saves — run by the 68060 itself on a
Picasso96 (or CyberGraphX) 8-bit screen. Offline play only. Everything WARPOS.md says about
running it (the screen-mode choice, pacing, double buffering, AHI, the controls,
`SWOS_AUTO_MATCH`, `SWOS_PRESENT_STATS`) holds here too; this file is what differs.

**Status (2026-10-22): it plays at ~49.8 fps in a match** -- most 10-second stretches exactly 500
frames, the rest 490-499 (the `[wos] alive` lines, without `SWOS_PRESENT_STATS`). Tested on the
A4000-class machine of WARPOS.md (68060, 256 MB fast RAM, Radeon 9200 on a Prometheus board, the
Radeon9200.chip Picasso96 driver). Menus, CPU-vs-CPU matches (`SWOS_AUTO_MATCH`), music and
effects through AHI (16 kHz here). A match frame is ~17.5 ms of work: the game ~10 (the pitch
redraw ~6.8 of it), the mixer ~2, getting it to the card ~5.

## Building

```bash
make -f Makefile.rtg060 -j$(nproc)      # -> bin/SWOS.060
```

Bebbo's `m68k-amigaos-gcc` 6.5 (`PREFIX`, default `/opt/amiga`) with **libnix**
(`-noixemul`). The compiler writes the hunk program itself: no `elf2warpos`, no stub.
`build/rtg060/m68k/SWOS.debug` is the same link unstripped, for `addr2line`.

- **Not the `m68k-amiga-elf` toolchain of `Makefile.amiga`**: that one is `-nostdlib`, the
  hardware build's, and has no hosted libc to give the chunky code.
- **Not Bebbo's newlib** (the default when neither `-noixemul` nor `-mcrt=` is given): it has
  no `stat`, `mkdir`, `signal`, `gettimeofday` or `<dirent.h>`. libnix has them all and lacks
  only `funopen` (below).
- `-m68060 -mhard-float`: a full 68060. An LC060 has no FPU and is not a target (the music's
  filter is floating point, `rjp1.c`).
- **The stack**: libnix's `swapstack.o` gives `main()` the 1 MB `__stack` asks for
  (`platform_wos.c`) — the same as the WarpOS stub's `--stack`. Nothing would pull that object
  into the link, so the makefile says `-u ___stkswap`; its `__stkinit` must be in
  `___INIT_LIST__` (check with `objdump -s` if the link changes).
- No CyberGraphX headers ship with the toolchain's NDK, and AHI's inline macros are under
  `defines/`: `include/rtg_cgx68k.h` holds the six CyberGraphX calls and the tags the game
  uses, from CyberGraphX's published interface. The WarpOS build keeps the SDK's own headers.

## How it differs from WarpOS

`include/swos_platform.h` gives this build `SWOS_RTG060_BUILD`, `SWOS_AMIGA_RTG_BUILD` and
`SWOS_CHUNKY_BUILD`. The platform files are WarpOS's — `platform_wos.c`, `input_wos.c`,
`audio_wos.c` — and what both Amiga RTG builds do (PROGDIR:, the save folder, no MULTIPLAYER
button) gates on `SWOS_AMIGA_RTG_BUILD`.

**`__m68k__` no longer means the hardware build.** This compiler defines it, so every test for
the custom-chip build reads `defined(__m68k__) && !defined(SWOS_RTG060_BUILD)`. The one left
alone is `endian_helpers.h`'s: big-endian is right for both.

| | WarpOS | 68060 |
|---|---|---|
| clock (`rtg_clock.c`) | `GetSysTimePPC` | `timer.device`'s `ReadEClock` |
| short wait | `WaitTime` (oversleeps ~9-13 ms) | a `UNIT_MICROHZ` request |
| frame pacing's spin | the last 21 ms — the whole frame — on the PPC, free for the 68k | the last 2 ms only: a spin here IS the 68k, and every task at the game's priority waits through it |
| memory AHI reads | `dcbf` + `sync`: the 68k does not snoop the PPC's cache | nothing to flush, one CPU: a compiler barrier |
| the log | a cookie stream (`fwopen`) into a 32 KB buffer, written out every 2 s; copied to the AMIGABRIDGE port with `SWOS_LOG_BRIDGE=1` | `stderr` reopened on `SWOS.log` with that buffer, closed and reopened every 2 s so its size on disk stays current. No bridge copy. Until the game folder is known, lines go to the Shell |

## What this machine costs, measured

`SWOS_PRESENT_STATS=1` prints these once at start and every 250 frames:

| | measured | what follows |
|---|---|---|
| CPU writes into the card (Zorro III -> Prometheus aperture) | 5.3 MB/s for whole rows; the Radeon9200 driver measures a 6.1-6.3 MB/s ceiling (p96-driver docs/04-performance.md) | a full 336x272 frame is ~17 ms: it must not cross the bus every frame |
| fast RAM | write 25 MB/s, read 40 MB/s, copy 20 MB/s; a 16-byte cache line missed ~0.4 us | touching a whole frame (91 KB) costs ms; scattered small accesses cost more than their bytes |
| CPU | 1M register-only loop passes in 70 ms | a normal 50 MHz 68060 |
| a shift of the picture on the card (BltBitMap -> the driver's BlitRect) | ~0.4 ms | the GPU moves the picture, not the bus |

The WarpOS build never met the first: its PPC writes the card over PCI (~30 MB/s).

## Getting the frame to the card (platform_wos.c, "Scrolling on the card")

In a match the frame is the pitch, shifted with the camera, plus what was drawn on it. So:

1. The card shifts what it shows by the camera's move (one `BltBitMap`), so the pitch needs
   no sending. The probe times the first 50 shifts: over 3 ms each means a board without
   a hardware blitter, and the row path takes over.
2. Every writer of the frame marks where it wrote, BEFORE writing (`Render_MarkRect`,
   platform_sdl.h): the sprite blit, the glyph blit, `fillRectChunky`, the full-frame
   copies, the crowd tiles. What is sent is those rectangles of this frame and of the last
   (shifted: the pitch goes back where a sprite was), and the strip the shift uncovered --
   in 4-pixel units (a byte over the bus costs a longword), from a bitmask per row, runs
   found with count-leading-zeros. ~7 KB a frame instead of 60-90.
3. Nothing is compared in a match: on this memory comparing cost more than sending.
   Instead VERIFY_ROWS rows are read back from the card after each upload and held
   against the frame -- the whole picture every ~1.4 s. A difference (a writer that did
   not mark) sends everything and compares whole frames for 50 frames. Outside a match
   every frame is compared against a shadow of the card.
4. All of that is prepared before the shift, and the shift and the upload go back to back:
   shifted first, the players and the ball moved with the pitch for the ~8 ms of the
   preparing, and shook against the grass.

`SWOS_NO_SCROLLBLIT=1` keeps the row-by-row path. On WarpOS it is off unless
`SWOS_SCROLLBLIT=1`.

## The game's own time

Shared code, the same bytes on every target, host-tested against the old loops:
`DrawChunkyPitch` (row by row in aligned longwords; it used to clip every pixel: 18 ms on
the 68060), `blitChunkySprite` (clipped once per sprite), `RJP1_MixSamples` (its volume
product out of the loop). For this build only: the music's low-pass filter in fixed point
(the float version was ~40% of the mixer), its own `memcpy` (libnix's calls `CopyMem`),
`getenv`/`setenv` over `GetVar`/`SetVar` (libnix's never read `ENV:`).

Tried and taken out:

- **Drawing the pitch lazily**, a tile at a time where something is drawn or sent. It halved
  the game's time (10 -> 4.6 ms), but the screen showed displaced pitch features that no check
  could see (the frame held the same pixels as the card). Not understood; not worth a picture
  nobody can trust.
- **MOVE16** for the redraw (a line written without the cache first reading it): the machine
  hung at once. MOVE16 needs memory that bursts; this one's does not.
- **Writing the redraw row by row in aligned longwords** (shift-merge, or a row buffer): slower
  than the plain tile copy (8.5-16 ms against 6.8). On this memory, writing is the cost, not
  its alignment.

Also this build: the log is not closed and reopened during a match (file-system work cost a
frame or two every 2 s), the frame pacing spins the last 5 ms (timer.device overslept 0.7 ms),
and the mixer runs at 16 kHz (`SWOS_AHI_RATE` to change).

## The compiler

Bebbo's gcc 6.5.0b merges a word clear and the long clear after it into one long clear, in
its peephole2 patterns and in its own backend optimiser: a packed struct's `u16 = 0; ptr =
0;` left the pointer's low 16 bits. It crashed the stadium menu at kick-off (UnpackMenu's
template reset kept `StadiumBeforeDrawLeftTeam`'s low half, `$0000xxxx`). `Makefile.rtg060`
builds with `-fno-peephole2 -fbbb=-`; each flag alone fixes some cases and not others.

A crash writes its PC and the stack to `SWOS.log` and exits to the Workbench
(`SWOS_CRASH_REQUESTER=1` for the system's requester instead).
